# Seeds and scenarios

What evidence each investigation runs on, what is planted inside it, and
escalation texts you can paste. Every scenario below is deterministic: the
generators produce byte-identical files, and the answer keys live in this doc,
`README.md` and `sandbox/` — never in app code or anything the app serves at
runtime.

## Seed sets at a glance

| Scenario | Seed | Load via | Run labelled |
| --- | --- | --- | --- |
| Northwind / Meridian — one incident | `public/demo/` (generated by `scripts/gen-demo.ts`) | Start page **Load Northwind scenario**, or `/upload` | `demo` → synthetic |
| Contoso / Orbit — two independent issues | `public/multi/` (checked in) | Start page **Load multi-issue scenario** | `demo` → synthetic |
| Bright Market / Lumen Ledger — four-tenant workspace | `public/realistic/` (generated by `scripts/gen-realistic.ts`) | `/upload` folder or zip; `npm run real:smoke realistic` | `upload` (real smoke) |
| Live sandbox workspace — five incidents | `sandbox/` seed engine | `npm run sandbox:seed -- --run`, then a live pull | `pull` → live |

Two smaller variants ride on the same seeds:

- **Vague escalation** — the Northwind export with no client named and a
  content-free complaint; used by `npm run real:smoke -- vague` to prove the
  report never presents a guessed scope as confident.
- **3-record Jira+email sample** — the tiny fixture in
  `tests/ui/model-report.spec.ts` that drives the report page invariants.

## 1. Northwind / Meridian (synthetic demo)

**Seed:** `public/demo/` — 7 files: `jira-meridian.json`,
`northwind-emails.mbox`, `escalation.eml`, Slack `users.json`, `channels.json`
and two channel transcripts. Regenerate with `npm run demo:gen`.
Roughly 45 records across Jira, email and Slack.

**What is planted:**

| Fragment | Where it lives |
| --- | --- |
| Root cause: UTC date handling shipped in 4.12 (`MER-87`) | `MER-87` comment + `MER-101` comment + Slack `meridian-billing` |
| Release went live 2024-09-10 | Slack, 2024-09-10 |
| Promise: "fix will ship in the Sep 24 release" | Email from L. Chen, 2024-09-20 + Slack |
| Premature `Resolved` (2024-09-26) while QA still fails | `MER-101` changelog vs Slack QA, 2024-09-25 |
| No handoff: Lin Chen on leave until Oct 2, no coverage | Slack, 2024-09-20 |
| Four unanswered client chases | Emails 2024-09-27 → 2024-09-30; last reply 2024-09-24 |
| Jira silence ~13 days | 2024-09-10 → 2024-09-23 |
| Cross-source reference `SUP-2231` | Email, 2024-09-18 |
| Identity trap: `L. Chen <l.chen@northwind.example>` = `Lin Chen` | Email vs Slack |
| Undocumented client call | Escalation email ("as discussed on our call") |
| ~30% noise | `MER-102`, `MER-104`, timesheet mail, webinar, `general` chatter |

**Expected shape:** one issue, one broken promise, a premature closure, an
unanswered client, and the undocumented call as a gap. The Sep 24 release
reaching production is never recorded.

### Escalation examples

The bundled `escalation.eml`, verbatim:

```text
From: Priya Nair <priya.nair@northwind.example>
To: Marcus Webb <marcus.webb@meridian-software.example>
Date: Tue, 01 Oct 2024 08:30:00 +0500
Subject: Escalation: invoice totals still wrong after 4.12
Message-ID: <m11@northwind.example>
In-Reply-To: <m7@northwind.example>

As discussed on our call, our Meridian Billing vendor carries a contractual SLA on invoice accuracy.

Totals are still wrong five days after the promised Sep 24 fix, and we have had no reply to four messages.
```

The start page's prefilled text (client **Northwind Logistics** declared):

```text
Northwind reports that our Meridian Billing vendor's invoice totals have been
wrong since release 4.12, our finance team is blocked, and we have not had a
reply to four messages. Please explain what happened and when this will be
fixed.
```

Same escalation without declaring the client tests the `partial` scope path
(the report warns that the scope is unconfirmed).

## 2. Contoso / Orbit (synthetic, two independent issues)

**Seed:** `public/multi/` — `jira-orbit.json`, `mailbox.mbox`,
`escalation.eml`, Slack `users.json`, `channels.json` plus `orbit-support`,
`general` and `orbit-eng` transcripts. Checked in, not generated.

**The two issues:**

1. **Blank VAT invoice totals after 2.1.0**
   - Root cause ticket `ORB-150` (`BILLING-V2: VAT rounding regression`):
     integer rounding drops fractional cents.
   - Main ticket `ORB-101`: promised for the **Sep 20** release, marked
     Resolved on 2.1.3 (2024-09-21) while the finance sandbox still shows
     blanks, reopened 2024-09-26, fixed in **2.1.4** (2024-09-28).
2. **Finance SSO failing after the identity migration**
   - Root cause ticket `ORB-160`: identity-service 3.4 dropped the SAML
     signing certificate.
   - Main ticket `ORB-140`: promised for the **Sep 26** release, marked
     Resolved while finance still failed, fixed in **3.4.1** (2024-09-29/30).

**What is planted:** per-issue promise, owner and fix version; the client's
chases live in the shared `general` room (plus the mailbox). The evidence has
four tickets — two mains plus their two root-cause tickets — but the escalation
defines **two** independent issues, so the plan must split exactly two.

### Escalation examples

The start page's prefilled text (client **Contoso** declared):

```text
Contoso has two independent issues. First, VAT invoice totals have been blank
since the 2.1.0 upgrade; the fix was promised for the Sep 20 release and the
ticket was closed while the totals were still blank. Second, finance users
cannot sign in since the identity migration; the SSO fix was promised for the
Sep 26 release and still fails. Our chases on 22 and 23 September went
unanswered. Explain what happened on each issue and when each will actually be
fixed.
```

The bundled `escalation.eml`, verbatim:

```text
From: Dana Okafor <dana.okafor@contoso.example>
To: Ravi Menon <ravi.menon@orbit.example>, Leo Park <leo.park@orbit.example>
Date: Mon, 30 Sep 2024 08:00:00 +0000
Subject: Escalation: two independent issues, four unanswered chases

This is a formal escalation. We have two independent issues: blank VAT totals
since 2.1.0, and SSO login failing for finance since the identity migration.
The VAT fix was promised for Sep 20 and the SSO fix for Sep 26. Both dates
passed without a working fix, our chases on 22 and 23 September went
unanswered, and we still have no explanation or dates. Please explain what
happened on each issue and when each will actually be fixed.

Dana Okafor, Finance Lead, Contoso
```

Control: the Northwind escalation above is one incident and must stay one
issue — a failed fix, a premature closure and unanswered chases are facets,
not separate issues.

## 3. Bright Market / Lumen Ledger (synthetic, four tenants)

**Seed:** `public/realistic/` — 14 seed files (+ `manifest.json`), **276
records**, generated by `npm run realistic:gen`. One evidence set holds four
engagements; only one is the target.

| Tenant | Tickets | Channels | Role |
| --- | --- | --- | --- |
| Bright Market (client) vs Lumen Ledger | `LUM-*` | `lumen-general`, `general` | target |
| Acme Corp | `KST-*` | `kst-rotas` | distractor |
| Halcyon Retail | `VEG-*` | `vega-payments` | distractor |
| Vertex Systems | `RAV-*` | `rav-core`, `vertex-billing` | distractor |

**What is planted (all cross-source fragments):**

| Fragment | Where it lives |
| --- | --- |
| Root cause: `KESTREL` billing-v2 moved VAT rounding to integer math in 5.3.0 | Comment on the *linked* ticket `LUM-804` only — never in the escalation or `LUM-811` |
| Promise: "fix scheduled for the Sep 20 release" | Email 2024-09-02 (Ravi Menon) + Slack 2024-09-18 + Jira |
| Contradicting claim: releasebot "5.3.3 is live: includes billing-v2 fixes" | Slack `lumen-general`, 2024-09-20 |
| Premature resolution: `LUM-811` Resolved 2024-09-21 ("exports verified on our side") | Jira vs QA re-run in Slack, 2024-09-21 |
| Handoff: assignee Alex Weinstein → Ravi Menon | `LUM-811` changelog 2024-09-22 only |
| Leave: Nadia Chen on leave | Slack `lumen-general` 2024-09-09 only |
| Unanswered chases ×3 + one email | Vendor's shared `general` room 2024-09-22/23 + mailbox |
| Real fix: 5.3.4 on 2024-09-28, confirmed by the client | Email 2024-09-28 |
| 8-day silence | 2024-09-09 → 2024-09-17 (no records at all) |
| Traps | Canned-support twin emails (Acme/Vertex); `vertex-billing` distractor channel; DST-shifted header on a competing tenant's mail; ~85% noise |

### Escalation variants

The seed's own `escalation.eml` is the **named + declared** case:

```text
From: Dana Okafor <billing@brightmarket.example>
To: Lumen Ledger support <support@lumen.example>
Date: Sat, 28 Sep 2024 11:15:00 +0800
Subject: Escalation: Bright Market (LUM-811) — invoice VAT totals and a four-week run-around

This is Bright Market's formal escalation on LUM-811 (VAT invoice exports show blank totals).

The totals have been blank since your 5.3.0 upgrade four weeks ago. We were told the fix
would ship in the Sep 20 release; instead your bot announced 5.3.3 fixes and the ticket was
closed while our finance sandbox still showed blank exports. Our chases on the 22nd and 23rd
went unanswered.

Please explain what happened and when this was actually fixed.

Dana Okafor, Finance Lead, Bright Market
```

Drop the client declaration (leave the **Client** field empty) for the
**named-only → partial** variant:

```text
Bright Market reports that our VAT invoice exports show blank totals since the
5.3.0 upgrade, the Sep 20 fix never arrived, and our chases went unanswered.
```

A **vague + declared** variant (client "Bright Market") should resolve
`partial` with caution:

```text
The totals in our billing exports have been blank for weeks and nobody replies.
```

A **vague + nothing** variant must come back unscoped and say every stored
record was searched — this is what `npm run real:smoke -- vague` asserts with:

```text
Everything about our billing module has been broken since the last update.
Nobody replies.
```

To run it: `npm run realistic:gen`, then upload the folder/zip on `/upload`
(with or without the client), or run `npm run real:smoke -- realistic` against
the built app with real credentials.

## 4. Live sandbox workspace (`sandbox/`)

A real Jira Cloud site and Slack workspace seeded with five independent
incidents, for live-pull testing against actual APIs. `sandbox/manifest.json`
records every issue, channel and message timestamp;
`sandbox/answer_key/incident_N.json` holds the full ground truth;
`sandbox/escalations/incident_N.txt` holds the escalation to paste; the scoring
rubric is `sandbox/scoring_rubric.md`.

| Incident | Domain | Project | Channels | Escalation file |
| --- | --- | --- | --- | --- |
| 1 | Billing — invoice totals | `SEED1` | `#seed1-eng`, `#seed1-ops`, `#seed1-client` | `incident_1.txt` |
| 2 | Mobile app — push notifications | `SEED2` | `#seed2-*` | `incident_2.txt` |
| 3 | Data pipeline — nightly exports | `SEED3` (+ `SEEDX`) | `#seed3-*` | `incident_3.txt` |
| 4 | Auth — SSO login failures | `SEED4` | `#seed4-*` | `incident_4.txt` |
| 5 | Logistics — carrier events | `SEED5` (+ `SEEDX`) | `#seed5-*` | `incident_5.txt` |

`SEEDX` is a shared platform project with cross-project issues for incidents 3
and 5. Story day 0 is 2026-10-17; the seeded "today" is day −1.

**Plant per incident:**

- **Incident 1** — UTC date handling in billing 4.12 shifts invoice boundaries
  by a day; promise "fix by end of week"; ticket marked Done while QA fails;
  client chases unanswered.
- **Incident 2** — the real root cause hides in a noise maintenance ticket: the
  `firebase-messaging` 24.x bump made missing Android channel ids fatal; a
  retry workaround is retracted; a duplicate ticket carries divergent device
  data; severity stays Low.
- **Incident 3** — a shared-schema rename silently drops the last export
  partition; the first stated cause (scheduler retry storm) is a red herring;
  the owner leaves with an unaccepted handoff and the ticket moves backwards.
- **Incident 4** — certificate pinning shipped in idp-2.9 breaks when the
  client rotates its certificate; an undocumented call is referenced; Done is
  recorded while half the users still cannot log in.
- **Incident 5** — the shared shipment-id prefix is not stripped by the
  matcher; a promise is retracted in both Slack and the ticket; Done lands on a
  branch that was never deployed.

Common traps across the set: identity mismatch across tools, premature Done
contradicted by QA/production, promises with relative deadlines, red herrings
stated first, owners on leave visible only in Slack, unreachable handoffs,
undocumented calls, and client chasers that never get a reply.

### Escalation examples

These are the exact files the scoring rubric expects. All five, verbatim:

```text
We were told on 2 Oct that the invoice totals fix would be out by end of week.
It is now 14 Oct and totals are still wrong, and nobody has answered our last
two messages. Our finance close is blocked. We need the corrected invoices and
a credible date today.
```

```text
Push notifications for our drivers have been unreliable since app 3.7. We were
told a retry workaround fixed it, then pushes were delayed again. Now we read
the incident was closed as a duplicate of a Samsung-only issue, which does not
match our devices. We need the actual cause and a fixed build.
```

```text
Since pipeline 9.2 our nightly export is missing the last partition. We were
told the fix was booked for 9.3, but the ticket has since moved backwards and
the owner seems to be away. Two chasers have gone unanswered and 9.3 is days
away. We need an interim export and an owner we can reach.
```

```text
Admin logins broke for a full day after our scheduled certificate rotation,
then only half our users could log in. Support told us on a call that a
rollback would fix everything, but that call and any agreement never made it
into the ticket, and the ticket was marked done while users were still locked
out. We need a complete fix and to know who owns this.
```

```text
Tracking events have not matched our shipments since logistics 6.4, and drivers
have been routed blind for over two weeks. We were promised a reroute the next
morning, then told to ignore that. Your ticket now says done, but our
production dashboard still shows unmatched events, and two chasers went
unanswered. We need to know what actually shipped, when it reaches production,
and who owns this.
```

Each contains a mix of true, false and unverifiable allegations —
`escalation_allegations` in the matching answer key grades every sentence.

**Commands** (see `sandbox/README.md` for credential and API constraints):

```bash
npm run sandbox:seed -- --dry-run              # plan only, writes nothing
npm run sandbox:seed -- --run                  # idempotent seed content
npm run sandbox:seed -- --verify               # re-read Jira + Slack and diff against the manifest
npm run sandbox:seed -- --repair-transitions   # replay planned status transitions only
npm run sandbox:seed -- --cleanup              # delete seed content
```

After seeding, connect the app to that Jira/Slack workspace (env vars) and run
a live pull for the incident; `sandbox/name_mapping.md` explains persona names
vs the API accounts.

## Conventions

- **Answer keys stay out of runtime.** No scenario name, ticket prefix, date,
  actor or expected sentence appears in `app/` or `lib/` — the app only ever
  reads what is in the registry.
- **Synthetic runs are labelled** `synthetic` in the UI and stored with
  `origin=demo`; cached results wear a `cached` chip and are keyed by model +
  pipeline version.
- **Fresh runs for tests/tooling** use the `cacheBust` form field or `?fresh=1`
  on the upload page — never text appended to the escalation, which the report
  renders verbatim.
- **Live checks** of any seed (real LLM, real credentials) are manual:
  `npm run real:smoke -- demo|realistic|vague|all` against `npm run start` on
  port 3000.
